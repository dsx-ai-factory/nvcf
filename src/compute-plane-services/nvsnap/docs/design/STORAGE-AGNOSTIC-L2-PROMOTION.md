## Problem

`internal/checkpointstore/percapture_pvc.go` (`PerCapturePVCBackend.Put`) is
the L2 tier: it turns one captured tree into a durable PVC that N restored
pods mount read-only. The rwx to rox transition is the only storage-specific
step; the lease, the single-copy write phase, the `pvc_promote_state` machine,
namespace scoping and GC are not. The transition has to work, with no copy
where the storage allows it, on:

| Storage | rwx to rox mechanism | Fan-out model |
|---|---|---|
| GCP Hyperdisk-ML | CSI VolumeSnapshot, then clone | one shared ROX PVC, N readers |
| AWS EBS (gp3/io2) | CSI VolumeSnapshot, then clone | RWO only: one clone per restore pod |
| NVMesh | none: reuse the same volume | N static ROX PVs sharing a transformed `volumeHandle` (zero copy) |
| CephFS / Filestore / EFS (RWX filesystems) | none: mount in place | one shared ROX/RWX PVC, N readers |

The shared-volume path follows NVCA's NVMesh model cache
(`pkg/storage/modelcache.go`, `doModelCacheNVMesh`): the primary PV is set to
`Retain` so deleting the writer PVC keeps the data; each consumer gets a
secondary PV, a `DeepCopy` of the primary with `ReadOnlyMany`, a
`VolumeHandle` rewritten by `updateSecondaryPVVolumeHandle` (a shared
read-only attach of the same volume) and a `ClaimRef` pre-bound to its RO PVC.
One backing volume, many read-only attaches, zero bytes copied.

## Design: a `Promoter` strategy + a `StorageProfile`

`PerCapturePVCBackend` keeps the storage-agnostic orchestration and hands the
storage-specific transition and the restore-side mount to a `Promoter`.

### Interface (`internal/checkpointstore`)

`Promoter` (`promoter.go`):

- `Promote(ctx, PromoteInput)`: called once per hash by the lease winner,
  after the write phase and the detach barrier, on the populated, detached
  `rwx-<hash>` writer PVC. Idempotent: a retry after a partial promote
  converges.
- `MountSpec(ctx, hash, VolumeMeta)`: the Volume and VolumeMount a restore
  pod uses. Per-pod strategies create the pod's artifact here; shared ones
  return the shared claim. `ErrNotFound` when nothing is promoted.
- `EnsureClaim(ctx, hash, ns)`: makes the shared restore claim exist in `ns`,
  since NVCF runs every chart in its own namespace. `ErrUnsupported` for
  per-pod clones.
- `Delete(ctx, hash, namespace)`: reclaims every artifact, including claims
  minted by `EnsureClaim`. Idempotent.
- `Caps()`: `StorageCaps` (`Snapshots`, `ReadOnlyMany`, `SharedVolume`), for
  startup validation and logging.

`PromoteResult` tells the orchestrator how restore consumes the artifact:
`SharedClaimName` (the one ROX PVC; empty when per-pod), `PerPod` (clones are
made in `MountSpec`; `Put` then publishes the logical `rox-<hash>` name,
`internal/checkpointstore/percapture_pvc.go`), `ReusedWriterVolume` (no copy;
informational). Not done: the agent's L2 fetch (`internal/agent/l2_fetch.go`
`fetchFromL2`) needs `EnsureClaim`, which per-pod clones do not support, so
for them that fetch treats L2 as unavailable and the cascade moves on.

`Backend.Mount` delegates to `MountSpec`, `Backend.Delete` to `Delete`. `Put`
keeps the lease, write phase, `waitForRWXDetach` and state machine, and calls
`Promote` where it used to snapshot and clone inline.

### Implementations

1. `SnapshotClonePromoter` (Hyperdisk-ML, EBS, any CSI driver with a
   VolumeSnapshotClass). `Promote` takes a `VolumeSnapshot` and waits for
   readyToUse. On a ROX-capable class (`Caps.ReadOnlyMany`) it clones one
   `rox-<hash>` ROX PVC. On an RWO-only class it sets `PerPod`, and
   `MountSpec` clones a `rox-<hash>-<vol.Name>` RWO PVC (`ensurePerPodClone`).
   Not guaranteed to be one per pod: the suffix is the volume name the caller
   passes, and the cachedir restore passes a fixed one (`cacheDirVolumeMeta`),
   so restores of one hash in one namespace share one RWO clone and can fail
   when scheduled on different nodes.
2. `SharedVolumePromoter` (NVMesh, RWX filesystems). `Promote` sets the
   writer PV to `Retain` and records its `CSI.VolumeHandle`: no snapshot, no
   copy, then creates the static secondary PV and its RO PVC, the handle
   rewritten by the profile's `volumeHandleTransform` (`none` reuses it
   verbatim). `MountSpec` looks the claim up and returns `ErrNotFound` when it
   is absent; `Backend.Mount` can then mint it with `EnsureClaim`.
3. `copy-per-pod` (RWO storage without snapshots) is a reserved strategy name,
   not implemented: `NewPromoterFromProfile` refuses it. On such storage L2 is
   not offered and the L3/L4 cascade serves restores.

### Selection: L2 StorageClass, provisioner and type, profile map

The agent resolves the strategy at startup from the L2 StorageClass
(`agent.l2.storageClass`), not the function StorageClass: on GKE the function
class `nvcf-sc` is RWO pd-ssd, while L2 fan-out needs a ROX-capable,
high-throughput class such as `hyperdisk-ml`. Both share a provisioner.

1. Read the L2 StorageClass: `.provisioner` and `.parameters.type`. The
   provisioner alone is ambiguous: `pd.csi.storage.gke.io` backs both
   Hyperdisk-ML and regular PD.
2. Look up the profile (`ResolveStorageProfile`) by `provisioner/type`, then
   bare `provisioner`, the `nvsnap-storage-profiles` ConfigMap winning over the
   built-in table (`builtinProfiles`) at each key. The ConfigMap extends or
   corrects the table per cluster with no agent rebuild.
3. Construct the Promoter (`NewPromoterFromProfile`) and log the class,
   provisioner, strategy and caps. If no profile matches, L2 is disabled
   (restore falls back to the cascade) rather than run on assumed capability.

The profile carries what the driver name cannot: the cluster-specific
`snapshotClass`, and whether the class is ReadOnlyMany. The built-in table
covers Hyperdisk-ML (ROX), pd-ssd and pd-balanced (per-pod clone), EBS
(per-pod clone), NVMesh (shared-volume, `nvmesh` transform, mount options
`ro,norecovery,nouuid` because xfs read-only multi-mount needs `nouuid`), EFS
and Filestore (shared-volume, no transform). A ConfigMap entry looks like:

```yaml
data:
  profiles.yaml: |
    # Key = provisioner[/parameters.type].
    pd.csi.storage.gke.io/hyperdisk-ml:
      strategy: snapshot-clone
      snapshotClass: hdml-images-snapshot-class
      readOnlyMany: true
    nvmesh-csi.excelero.com:
      strategy: shared-volume
      volumeHandleTransform: nvmesh
      mountOptions: [ro, norecovery, nouuid]
```

Two optional keys tune the cachedir restore's page-cache prewarm per class,
because whether parallel read-ahead helps depends on the volume, not the
model (the 70B A/B in `docs/results/BENCHMARK.md`):

- `prewarm` (default `true`): add the `nvsnap-prewarm` init container that
  reads the whole rox tree before the engine starts. Set `false` where one
  reader already saturates the volume.
- `prewarmParallelism` (default 6): concurrent readers in the sweep. Raise
  it where throughput scales with parallel readers.

A pod's own `NVSNAP_PREWARM=0` or `NVSNAP_PREWARM=1` overrides the profile.
The agent resolves the profile once at startup and hands it to the webhook,
so a ConfigMap edit takes effect on the next agent restart.

For AWS fan-out, an EFS profile (shared-volume) is the recommended path; EBS
per-pod clones are the fallback when no RWX filesystem is available.

## What stays storage-agnostic

- Hash-keyed Lease serialization, the single-copy mount-holder write phase,
  the `pending`, `writing`, `snapshotting`, `ready` state names (the
  `snapshotting` wire string now means promoting), namespace scoping
  (nvsnap#82), the `waitForRWXDetach` durability barrier (nvsnap#105; core
  CSI, needed by every block strategy) and the `nvsnap-l2-wait` restore gate.
- The restore webhook calls `Backend.Mount`; only the artifact differs
  (shared claim, per-pod clone or static-PV claim).
- Teardown is the existing retention controller's: on a hash's retention
  expiry it deletes the secondary PVs and PVCs first, then the primary PV
  (whose `Retain` policy would otherwise orphan it), releasing the backing
  volume. No new GC loop.
