# Restoring a Dynamo worker into a shared namespace as its own identity

Status: built for etcd discovery, behind `agent.identityRestore.enabled`
(default off); not yet run on hardware with this code. Kubernetes discovery is
not built. Scope: `internal/agent/identity_etcd.go`,
`internal/agent/identity_etcd_client.go`, `internal/agent/identity_peer_reset.go`,
and their call sites in `criu_group.go` (`captureGroup`, `checkpointInstance`,
`restoreGroup`, `lookupCRIUGroup`), `criu_auto_restore.go` (`restore`),
`grove_replicas.go` (`sharedCompanionsReason`) and `checkpoint_v2.go` (`dumpV2`).

## 1. Problem

A Dynamo worker computes its identity once at start-up: with etcd discovery,
its instance id is the ID of the etcd lease it registers under, and every key
it writes (endpoint registrations under `v1/instances/`, its model card under
`v1/mdc/`, its event channels under `v1/event_channels/`) is attached to that
lease. A checkpoint copies that identity. When many workers share one etcd,
NATS and frontend, nvsnap cannot capture the registry with one worker, so it
refuses such a worker (`grove_replicas.go` `otherDynamoWorker`, and the
`criu_group.go` refusal of a Dynamo rank with no etcd or NATS in its
namespace): restored, the copy's registration would be either a duplicate (its
source alive) or gone (its lease expired). Every such worker starts cold.

## 2. Idea

Do not change a restored worker's identity: make its own captured identity
valid again before it runs, and never have two live holders of one identity.
etcd lets a client choose the ID of a lease it grants, and refuses the grant
of an ID that is live, so the agent can re-establish the captured lease from
outside the process, and etcd itself rejects a second holder.

## 3. Capture

With the flag on, a candidate (`identityRestoreCandidate`) is a Dynamo
component on the pod network that names a plain-HTTP etcd literally in
`ETCD_ENDPOINTS` and does not use another discovery backend. When the group
capture would refuse it for the companions its namespace shares, or because
no etcd or NATS of its namespace is connected to it, it is captured alone:
companion discovery is skipped, so the shared frontend, etcd and NATS are never
stopped or captured with it.

Before the freeze the leader reads, from the worker's etcd, through the
worker's own network namespace (`podNetnsDialer`):

- every key under `v1/`; the worker's lease is the one lease that holds an
  instance registration named by its own ID in hex and a value naming the
  worker's pod address as a URL host. None, or more than one, refuses the
  capture.
- the lease's granted TTL and every key attached to it, with their values,
  read twice: the second read must find the same key set under the lease,
  each value unchanged, with an instance registration named by the lease
  and a key naming the address. A registration that changes between the
  reads is read again once, then refuses the capture.
  A key whose name, or whose value outside a URL host, names a rank's address
  refuses the capture: a restore could not rewrite it.

The identity (lease ID, TTL, pod address, the slot that holds the lease, the
etcd endpoints and the keys) is written into the group record with the
capture's outcome (`identity.*` keys). None of it is logged.

## 4. Resetting the source's outside connections

CRIU dumps established TCP connections in repair mode and closes them silently
when it kills the dumped tree, and it leaves its network lock (an nftables
table that drops the dumped connections' packets) in the pod's network
namespace. A peer outside the captured group never learns the source is gone:
a shared NATS kept a dead source's subscription for about six minutes in the
spike and handed it part of the restored worker's requests.

After a dump that killed its source (`endPeerReset`), the member's agent:

1. runs `criu net-unlock -D <images>` in the source pod's network namespace,
   which removes the dump's lock (the table is named by the dump's run id in
   the images);
2. for each connection the container had to a peer that is neither loopback
   nor a member of the group (any of its addresses), listed from the
   container's sockets once it is frozen and before CRIU runs, so the list
   is the sockets the dump takes, binds a socket to the connection's own address and port and
   connects to the peer. The peer, still holding the connection, answers the
   SYN with an ACK of its own sequence (RFC 5961); the probe answers that
   with a reset whose sequence is the ACK's, which the peer accepts
   (RFC 793), and drops the connection. The probe counts only when the
   peer is seen without the old connection: a SYN of the probe (its first,
   or the kernel's retransmit after the reset) is accepted, or refused. A
   challenge ACK alone proves only that the reset was sent. An unconfirmed
   probe is tried once more, then fails the capture; no probe runs past
   the capture's deadline. The probe is closed.

This needs no sequence numbers, no raw sockets and no change to the dump. It
runs only with the flag on, whatever a checkpoint request asks. A failure
fails the capture as one whose source must be replaced (the dead source is
never resumed), so no identity is
recorded whose source may still hold sessions. The connections listed are the
container's own, both directions.

Each member asked to reset reports it did (`CheckpointResult.PeersReset`);
a member that does not (an agent of an older version, or one with the flag
off, ignores the request) fails the capture, whose stopped pods are
replaced (`criu_group.go` `peersResetDone`).

The whole reset is bounded by `peerResetBudget` (30 s,
`identity_peer_reset.go` `afterDump`); probes run in parallel, those of one
local address and port one after another. The rule: every listed connection
must be confirmed reset within the budget, else the capture fails and its
dead source is replaced cold. A peer that drops the probe (a node gone, a
firewall or network policy, an SNAT path that loses it) therefore fails the
capture. Not verified: a peer reached through a Service address. The probe's
SYN goes to the Service address the connection used and is translated by the
node; that it reaches the same backend (the old connection's conntrack
entry) rather than another one, which would accept it and count as
confirmed, is assumed, not shown. A connection the kernel completes into a
listening socket's backlog after the inventory (the container is frozen, so
nothing accepts it) is not listed and not reset.

Only Dynamo's NATS request plane (`DYN_REQUEST_PLANE=nats`) is supported. On
the TCP request plane, Dynamo's default, an endpoint registers its address
as `{"transport":{"tcp":"<ip>:<port>/<path>"}}`; a restore does not rewrite
that form (`identity_etcd.go` `urlHostForms`), so the capture refuses the
identity (`readIdentity`, `strayAddress`) and the worker is not captured
with one.

## 5. Restore

With the flag on, a placeholder restores only from the record of its own
capture: when the record cannot be read, is not a capture to restore
(`recordUsable`), or no longer names the placeholder's checkpoint (replaced
by another capture, which may hold another identity), the restore is
refused and the pod starts cold (`identityBeforeRestore`).

A placeholder of a record with an identity is restored by the lone path
(`criu_auto_restore.go` `restore`) or the group path (`criu_group.go`
`restoreGroup`); both call `identityBeforeRestore` before anything is
restored:

1. claim the identity in the record (section 6);
2. wait for the captured lease to expire: at most the recorded TTL and a few
   seconds, since the source is dead. A lease whose TTL is renewed meanwhile,
   or that outlives the wait, is held by a live process: refused;
3. grant the lease with the same ID and TTL (etcd refuses a live ID:
   refused). The keys are not written yet: the frontend would route to an
   address nothing listens on while the checkpoint is fetched and restored;
4. keep the lease alive from the agent from the grant on (before the grant
   is recorded) through the restore, renewing it once at most half its TTL
   can be left. Once the process resumed, write every saved
   key with the captured pod address replaced by the new pod's (a key that
   another lease holds now is left as it is and fails the write), then
   watch the lease's TTL against what the agent's own last renewal explains:
   held above it for a whole TTL, the lease is renewed by the process and
   the agent stops, once it has renewed the lease one last time (a late
   sample may tell of a lease that expired since) and recorded the handoff
   (`identity.handoff`). A lease counts as above from the reply that showed
   it, and how long it stays above is measured to the latest sample's
   request. One renewal not its own (etcd renews every lease on a leader
   change) keeps it above for under half a TTL. A process whose
   keep-alive is not seen within three TTLs (at least a minute), or whose
   keys cannot be written, has its lease revoked and its pod deleted, so
   the frontend stops routing to a worker that does not keep its
   registration and no second restore takes the identity while it lives;
   that restore counts as a failed restore of its capture
   (`recordFailure`), so replacements that fail the same way end (a capture
   being verified fails, a verified one after its failure bound). A
   restore that fails revokes the lease and releases the claim.

An agent that restarts after a restore succeeded, before the handoff was
recorded, adopts the restored pod's lease on the pod's next event
(`considerRestoredIdentity`, from the lone pod's or the group leader's
node): it registers the keys the lease does not hold yet, keeps the ones it
holds (they may be newer than the capture's), and waits for the handoff as
above. A lease lost by then ends the pod and counts the restore failed.

A pod whose restore already had the lease granted (an agent that stopped
after the grant, which the record notes, whether or not it restored the
pod) adopts it; a claim alone is not enough, and a lease that cannot be
read is refused: a live lease is kept
alive rather than refused, and a restore that finds the engine already
running hands the lease over to it instead of revoking it.

A lone restore checks again, once the identity is set up, that its
placeholder is still the pod it was set up for (`criu_auto_restore.go`
`restore`, `samePlaceholder`), and binds the restore to that pod's UID
(`RestoreRequest.PlaceholderPodUID`): `Restore` refuses a container of
another pod found under the same name (`placeholderOfPod`,
`errPlaceholderReplaced`). A pod replaced under the same name is refused,
the lease revoked and the claim released, and the replacement is left to
its own restore.

A refused restore blocks no checkpoint. `identity_etcd.go`
`identityRefused` hands the pods to `settleRefused`:

- a pod gone, replaced, or no longer naming the refused checkpoint is left
  as it is;
- when any pod already runs its workload (a GPU process in its pid
  namespace, `podRunsWorkload`; only pods on the agent's node can be
  inspected, and the leader always is), the instance was restored before:
  every pod is kept, none started cold or deleted. Refused for an error
  that may pass (`refused_error`, an adopted lease that could not be read),
  the restore's next event decides again, so the identity can still be
  adopted;
- any other pod starts its workload cold in place;
- a pod that cannot start cold in place is deleted for its controller to
  replace, and only once the record counts a stall for the refusal
  (`chargeRefusal`), so replacements refused the same way stop at the stall
  bound. One refusal counts one stall, however often it is tried again
  (`refusedPods` on the record keeps every pod of the last refusal);
- a pod of which it cannot be told whether it runs a workload is never
  deleted: it starts cold in place, or is kept and tried again.

Each pod's outcome is its own: a pod that cannot be read does not keep the
other pods from starting cold or being deleted. A pod left unfinished (it
cannot be read, its stall cannot be counted, or its delete fails) is kept,
and its refusal is tried again. When no pod was started cold or deleted,
the restore's next event decides it anew (the lone pod's, or the group
leader's). Otherwise the restore cannot run again, and the agent that
refused it finishes the unfinished pods itself (`finishRefused`, backing
off up to 30 s, for at most a day): reading and deleting a pod works for
pods on any node. A refusal is also recorded on the group record before any
pod is acted on (`refusingPods`, by pod UID; when it cannot be recorded,
nothing is done and the restore's next event decides again), so that a pod
it left unfinished is finished by the pod's own agent on its next event
(`considerRefusing`), after the refusing agent restarted or past its retry
window. A pod started cold or deleted gives up its claim on the identity.

## 6. One live restore per identity

Two guards:

- the record names the restore that holds the identity
  (`identity.holder`, `namespace/pod/uid`), written with the record's
  version, so of two agents claiming at once one wins. A holder whose pod is
  gone or replaced is taken over; one whose pod lives, being deleted or
  not (a draining worker keeps its subscriptions), refuses the claim; an
  unreadable holder refuses it (fail closed). A refused or failed restore
  releases its claim;
- etcd refuses a grant of a live lease ID, whatever the record says.

## 7. Flag off, and rollback

With the flag off, capture behaves as before and the chart renders as
before. A record with an identity, written while the flag was on, is
invisible to admission with the flag off (`identityRecordVisible`), so its
configuration starts cold rather than restore without its lease; a
placeholder admitted while the flag was on and restored after it was turned
off is refused and starts cold (`refused_disabled`, counted once per
capture). For that, a restore reads its group record once more with the flag
off; records without an identity restore exactly as before. Turning the flag
off is the rollback. With the flag on, a restore whose record cannot be read,
or no longer names its checkpoint, is refused even when the capture held no
identity (section 5).

## 8. Observability

`nvsnap_identity_restore_decisions_total{decision}` counts each decision:
`captured`, `capture_refused`, `peers_reset`, `peers_reset_failed`,
`refused_live_lease`, `refused_held`, `refused_error`, `refused_disabled`,
`regranted`, `keepalive_handoff`, `keepalive_handoff_timeout`,
`keepalive_lease_lost`, `keys_write_failed`, `restore_aborted`,
`keeper_agent_stopped`. Every
value exists at zero from the agent's start. Each decision also logs one line
with the group key and reason, never the lease ID, keys or addresses.

## 9. Invariants

Against the invariants in `AGENTS.md`:

- Invariant 1: The source is stopped by its own dump only; the shared companions keep
  running throughout.
- Invariant 2: One restore per pod, and one live restore per identity (section 6).
- Invariant 3: An identity record holds one worker and no companions; admission still
  matches size and process configuration.
- Invariant 5: Every unreadable state refuses: registry, record, holder, lease.
- Invariant 7: The claim is released on refusal and on a failed restore, and
  kept for a pod that lost its identity until that pod is gone; the agent's
  keep-alive ends on handoff, timeout, failure or agent stop, and the lease
  then lives only as long as the process keeps it.

## 10. Not built, and not verified

- Kubernetes discovery (DynamoWorkerMetadata), host-network workers and TLS
  etcd endpoints are refused.
- One identity per configuration: a second replica restored while the first
  holds the identity starts cold. A pool of identities per configuration is
  later work.
- A refused placeholder still fetches its checkpoint before it is refused;
  a holder check at admission would save that.
- The dead source stays registered until its lease expires (its TTL) after
  the dump; the verification restore waits that long.
- Dual-stack pods: only the primary pod address is matched and rewritten.
- Dynamo's TCP request plane (its default): its registrations are not
  rewritten, so such workers are not captured with an identity (section 4).
- The identity is read before the freeze, not under it: a key the worker
  changes between the read and the freeze is not recorded (the read is
  repeated and compared, `identityStillHeld`, but not under the freeze).
- Not run on hardware with this code: the network-namespace dialer, the
  net-unlock of a dump's lock and the probe through a Service address, and
  Dynamo's own keep-alive resuming on the granted lease after a CRIU restore
  (seen in a manual spike, not with this code).
