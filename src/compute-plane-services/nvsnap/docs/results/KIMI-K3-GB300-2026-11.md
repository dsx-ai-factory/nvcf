# Kimi K3.1 Pro on GB300: cold starts, restores and scale-from-zero cycles, November 2026

The raw data behind the Kimi rows of [BENCHMARKS.md](../BENCHMARKS.md). Every value below is copied from the
test harness's output files (its log lines, the Kubernetes timestamps it printed, and the nvsnap group record it
saved), with node addresses, namespaces and function IDs removed. Times are UTC.

- **Workload:** an NVCF function serving `moonshotai/kimi-k3.1-pro` with Dynamo and vLLM: 4 GPU pods (a leader
  and 3 workers, one per node) plus the instance's own etcd, NATS and frontend pods (7 pods). On cluster A each GPU
  pod has 4 GPUs (the run notes, "4 nodes x 4 GPUs"; the harness output does not record it). A function of the same
  model and shape runs on cluster B.
  Each GPU pod downloads the model (1.56 TB, [NODE-MODEL-CACHE-2026-11.md](NODE-MODEL-CACHE-2026-11.md)) in an
  init container into a node-local volume. Engine versions: not recorded.
- **Capture:** `agent.captureMethod: criu`, the function opted in to multi-pod capture, gpushare on.
- **Non-default chart values, cluster A:** `agent.auth.enabled` (mode `required`), `agent.election.enabled`,
  `agent.nodeModelCache.enabled` (and `singleFlight` from `v0.2.91-rc22e` on), `agent.restoreCapturedAddress`,
  `webhook.skipUnusedInits` (so restore placeholders skip the model download init) and `webhook.gpushareIBV`, all
  `true`; `agent.rails.enabled: true` for `v0.2.91-rc22g` and `v0.2.91-rc22h` only.
- **Non-default chart values, cluster B:** `agent.l2.storageClass` set, `agent.auth.enabled` (mode `required`),
  `agent.election.enabled`,
  `agent.modelVolume.enabled`, `agent.rails.enabled` and `agent.restoreCapturedAddress`, all `true`.
- **Cluster A:** GB300 nodes, CRI-O, NVIDIA driver major 610 (the group record's `driver` field), no cluster storage
  tier (`agent.l2.storageClass` unset): checkpoints stay on the nodes' local disks. Sections 1 to 3.
- **Cluster B:** GB300 nodes (the agents' `gpu=NVIDIA-GB300` log field in other runs on this cluster in early
  November; the cycle output does not record it), containerd, with a cluster storage tier. Section 4.

measured by the agent that drives the group restore, from when it starts waiting for every restore placeholder pod to

## 3. Scale-from-zero restores that did not run, cluster A

2026-11-24, agent `v0.2.91-rc22t`: the harness deleted all 7 pods of the instance in one pass (etcd, NATS and the
frontend listed first) at 19:20:59, with a complete record of the configuration. In 30 minutes no new restore was
added to the record (`FAIL: no restore recorded within 30 min`). A later version of the harness deletes the
companions only once the GPU pods are gone, because a companion recreated while a GPU pod of the instance still runs
is admitted cold and the group restore waits for it. Whether that caused this failure is not verified.

2026-11-25, agent `v0.2.92-rc1`: the same check after the capture of section 2 (05:51 to 06:24) also ended
`FAIL: no restore recorded within 30 min`. The harness lost cluster access during the run (`Unable to connect to the
server` in its output), so this failure may be the harness's.

## 4. Scale-from-zero cycles, cluster B

Each cycle deletes the instance's 4 GPU pods and then its etcd, NATS and frontend pods, and waits until all 7
replacement pods are restored (annotation `nvsnap.io/criu-restored` newer than the delete) and Ready, polling every
20 s. "Restore" is the seconds from the delete to that point, so it includes the old pods' teardown ("teardown", the
seconds until the old GPU pods were gone). A cycle passes when, after a 5-minute soak, no container restarted, the
answer to one `What is a*b?` request is right and the teardown took at most 180 s. A cycle that fails ends the run.
Before cycle 3, the harness removed one worker checkpoint's recorded restore length on every node (`precycle.sh`).
GPUs per pod: not recorded in this output.
