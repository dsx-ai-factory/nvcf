# Will nvsnap work for my workload?

One row per workload shape or platform choice. Statuses and refusals come from the code on `main`; a GPU run names
the nvsnap build it ran on (pre-release builds). Each row has one status:

- **Supported**: on by default, and tested on GPUs (the evidence names the run).
- **Opt-in**: behind a setting that is off by default.
- **Refused**: nvsnap detects it and does not checkpoint it; the workload runs and starts cold (or from the cachedir
  fallback) as it would without nvsnap.
- **Not tested**: nothing on record shows whether it works.

A refusal never fails the workload. The agent logs why, and the log line in each row is what to search for. The
admission webhook needs cert-manager (`webhook.enabled`, `values.yaml`). GPU runs
are recorded in `docs/results/`; measured times are in [BENCHMARKS.md](BENCHMARKS.md).

## Capture method

The chart value `agent.captureMethod` picks one method for the whole cluster
([values.yaml](../deploy/helm/nvsnap/values.yaml)).

| Method | Status | Setting (default) | What happens | Evidence |
|---|---|---|---|---|
| cachedir: the engine's model and compile caches are captured and mounted into a fresh start | Supported | `agent.captureMethod: cachedir` (the default) | The engine still starts, but skips the model download and reuses compiled kernels and graphs | Chart default: `values.yaml`. GPU runs: [HELM-CHART-CACHE-2026-09.md](results/HELM-CHART-CACHE-2026-09.md) sections 1, 4 and 5 (H100, agent v0.2.75-election2 and -election6, 2026-09-25), with the admission election and a cluster storage volume, both off by default |
| GPU checkpoint/restore: the running processes and their GPU memory are checkpointed with CRIU and the gpushare library, and restored in place of a fresh start | Opt-in | `agent.captureMethod: criu` | A restored pod resumes the captured engine; it does not start it again | `captureMethod` in `values.yaml`; `criuIsDefault`, `internal/agent/criu_auto_restore.go`. GPU runs: every row below marked Supported |
| cachedir as the fallback of a CRIU cluster | Supported | none: automatic under `captureMethod: criu` | A configuration whose CRIU capture failed, whose restore failed, whose pods do not start under the gpushare library, or whose cluster drivers CRIU cannot use (see [Platform](#platform)) gets the cachedir instead | `criuFallbackReason`, `internal/agent/criu_fallback.go`; `CRIUFallback`, `internal/webhook/criu_fallback.go`; [CRIU-CAPTURE-FALLBACK.md](design/CRIU-CAPTURE-FALLBACK.md) §2.2, §2.8. GPU run: scenarios `mptcp1` and `libfail1`, [CONFORMANCE-GB300-2026-11-02.md](results/CONFORMANCE-GB300-2026-11-02.md) (agent v0.2.89-mv216) |

The rows below are for `agent.captureMethod: criu`.

## Networking and RDMA

| Case | Status | Setting (default) | What happens | Evidence |
|---|---|---|---|---|
| NCCL between pods with no RDMA device | Supported | none | Captured like any other process state | GPU run: scenarios `sts2` and `sts8`, whose pods request no RDMA device ([CONFORMANCE-GB300-2026-11-02.md](results/CONFORMANCE-GB300-2026-11-02.md)) |

| `hostNetwork: true` workload pods | Not tested | none | No code handles them specially | No GPU run on record |
