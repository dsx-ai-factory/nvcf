# Will nvsnap work for my workload?

One row per workload shape or platform choice. Settings and refusals come from the code on `main`. The GPU runs used
pre-release agent builds, `v0.2.75` to `v0.2.92` (each row names its build). The chart's default agent image
(`agent.image.tag: v0.2.70-rminject1`, `values.yaml`) is older than all of them.

Each row has one status:

- **Supported**: needs no setting beyond its section's capture method, and a GPU run shows it.
- **Opt-in**: needs a setting that is off by default; the Setting column names it.
- **Refused**: nvsnap detects it and does not checkpoint it; the workload runs and starts cold (or from the cachedir
  fallback) as it would without nvsnap.
- **Not tested**: no GPU run shows whether it works.

The **Tested on GPUs** column says whether a GPU run shows the row, and which non-default settings that run had. A run
with cluster storage or rails on does not show that the row works without them. "No" means code and unit tests only.

A refusal never fails the workload. The agent logs why, and the log line in each row is what to search for. The
admission webhook needs cert-manager (`webhook.enabled`, `values.yaml`). GPU runs
are recorded in `docs/results/`; measured times are in [BENCHMARKS.md](BENCHMARKS.md).
